## Key contributions

- **Three-step validation, binary-level and language-agnostic.** (1) *Determinism testing:* NVBit instruments the compiled SASS, inserts delays of up to 5,000 cycles before selected memory instructions, and compares the output byte-for-byte with an unperturbed run. It needs no source or compiler, so CUDA, Triton, Gluon, and CUTLASS kernels are handled identically. (2) *Reduction:* an agent (Copilot CLI on GPT-5.6 at maximum reasoning effort) rewrites both candidate and reference into "reduced-concurrency" kernels — no barriers, atomics, cooperative launches, or warp primitives — accepted only if they reproduce the original's output **bitwise** on every tested input. (3) *Proof:* agents write a shared algebraic specification from the reference alone, port both reduced kernels into Kuiper (a verification language on the F*/Pulse concurrent separation logic that covers a CUDA subset), and prove both satisfy it over the **real numbers**, so numeric tolerances disappear from the statement.
- **Trust structure.** Agents write specifications, Kuiper programs, and proofs but "do not serve as correctness oracles": the proof checker accepts or rejects. Specification tightness was checked by hand for every case ("we inspected every specification by hand and found each one to be tight"); automated tightness certification is future work.

## Summary

Applied to 100 GPT-5.6-generated KernelBench Level 1 candidates that had all passed the benchmark's shipped tolerance tests, to fused multilayer-perceptron GEMMs in CUTLASS, Gluon, and Triton, and to three published megakernels. Hardware: four NVIDIA H100 PCIe (sm_90, CUDA 13.0). The pipeline found two incorrect KernelBench candidates that the official checker accepted, proved eleven candidates equivalent to their references, established equivalence across the three fused-GEMM implementations, and surfaced four previously unreported nondeterminism issues in megakernels, two of them clear bugs, which agents then repaired with performance changes under 2% on three of the four.

## Key takeaways

- **KernelBench study (Table 1, 31 kernels evaluated):** 15 bitwise-identical to the reference after determinism testing; 2 rejected as empty kernels that still passed the shipped tolerance tests (ELU and hardtanh — "Both nonetheless pass the tolerance tests KernelBench ships with"); 11 reduced and formally verified; 2 inconclusive for missing Kuiper features; 1 inconclusive because it uses a numerical approximation (a Taylor-series sigmoid) that an exact real-number specification cannot accept. Of 85 non-bitwise-identical pairs, only 14 went through the full workflow "which keeps the study tractable."
- **Cost per kernel (Table 2, medians over the 14 kernels carried through the full workflow — 11 proved, 3 inconclusive — wall clock):** determinism test 1.47 min; agent reduction 29.3 min (12.6–74.4) at 39.1K input / 8.1K output tokens; specification and proof 112 min (44.6–250) at 5.54M input / 65.6K output tokens; total 143 min (58–344). Specification and proof dominate; agents read about 85 input tokens per output token.
- **Fused GEMM across languages (§6.3, hidden 8,192, FFN 29,568, 4,096 rows):** none of CUTLASS, Gluon, or Triton matches the PyTorch reference bitwise; Gluon and Triton match each other, so one proof (Gluon) plus bitwise tests covers both. Determinism testing 8–10 min and reduction 11–17 min per variant; proofs about an hour each. Compute Sanitizer reports nothing on any variant.
- **Megakernels (§6.4, Table 4):** LUCE (24-layer hybrid DeltaNet/attention decode step) had a grid-barrier counter reset racing with arriving blocks and a scratch address missing block and head offsets so attention blocks shared a buffer — both bugs; FlashMoE's atomic slot reservation and FastMoE's atomic capacity pruning make dropped tokens depend on arrival order, which the authors list as "under discussion." Agent repairs changed warmed-call latency by −1.4%, −1.6%, +0.8%, and +10.5% (FastMoE). After repair FastMoE is bitwise identical to PyTorch; FlashMoE was reduced but not specified (Kuiper lacks argmax); LUCE was not reduced (Hopper warpgroup instructions impose a 128-thread floor). The authors also attempted "Mirage", citing the MPK paper (Cheng et al., 2025, "MPK: a compiler and runtime for mega-kernelizing tensor programs"); it "hung when run under our determinism tester," so nothing is reported for it. Ada-MK is not mentioned.
- **Oracle strength (RKB-Mutant):** of 143 runnable mutants, the determinism tester plus bitwise comparison catches 92 (64.3%); misses are 3 in dead code, 28 races that never change output, 20 intra-warp races the instrumentation cannot reach. 90 of the 92 catches already mismatch without perturbation.
- **Floating point:** the proof is equality over reals. Bit-equality between each layer (original ↔ reduced ↔ Kuiper) is established by testing, not proof, so rounding and reassociation differences between candidate and reference are outside the proved statement.

## Why it matters for this survey

This is the strongest answer so far to the guide's validation-contract requirement: it shows a route from "passes `allclose` on five inputs" to "proved equivalent to the reference specification," applied to the same kernel population that most agent speedup claims draw from. Three consequences for design. First, the two accepted-but-wrong KernelBench candidates are a direct instance of the contract-evasion row in the validation table and of the oracle gap that [Measuring the Checker](measuring-the-checker.md) quantified with synthetic mutants; RESOLVE supplies the real-candidate counterpart. Second, the cost structure — hours and millions of input tokens per kernel, dominated by specification and proof — means this verification level is affordable only where the artifact is reused heavily (the per-workload-versus-offline question) or where a bug is expensive, as in production megakernels; it is not a per-candidate filter inside a search loop. Third, the megakernel findings (LUCE, FlashMoE, FastMoE; MPK, which the paper calls Mirage, hung under the tester and is not reported, and Ada-MK was not tested) are a correctness audit of the whole-step compilation direction that [MPK](mpk.md) and [Ada-MK](ada-mk.md) also represent; the paper makes no priority claim, saying only that such kernels are, as far as the authors are aware, out of reach for existing rigorous validation: the integration gains are real, and so are arrival-order dependences that tolerance tests never see. The paper's closing claim, that "agents can optimize aggressively when they can rigorously check their results," is a hypothesis this guide already states in the wider-synthesis question; RESOLVE lowers the cost of testing it rather than settling it. Read with [AI as a Compiler](ai-as-compiler.md), whose verified-versus-numerical speedup gap measures the same checker-coverage limit from the other side, and with the [KernelBench-Verified](kernelbench-verified.md) protocol changes.

## Limits / caveats

- Not a race-freedom proof: "RESOLVE computes no happens-before relation"; it detects observed nondeterminism under perturbation. Intra-warp races, races that never change output, and asynchronous loads it cannot delay are out of reach ("need compiler support or a static analysis").
- Legitimate nondeterminism is rejected by construction (floating-point `atomicAdd`; one of the 100 KernelBench kernels). Approximating kernels are rejected because "correctness of an approximating kernel simply cannot be determined without reasoning about numerical tolerance"; error budgets are future work.
- Fixed shapes, ten input distributions, KernelBench Level 1 only; fourteen full-pipeline cases. Reduction rejects barriers, atomics, cooperative launches, and warp primitives, and the agent's reduction success rate is not reported.
- Single model family for the agent steps; proof cost is not shown to scale to attention-class kernels with producer–consumer pipelines, which Kuiper does not yet formalize. The artifact is referenced but no URL appears in the text read.
- Experiment that would settle more: run the pipeline on the accepted candidates of a published agent speedup study (for example a KernelBench-X or D2K-Bench leaderboard) and report how many verified, how many were rejected, and what the geometric-mean speedup is among verified kernels only.
