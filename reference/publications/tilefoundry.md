## Key contributions

TileFoundry is a platform in which a coding agent (every example uses Claude Code with `claude-opus-5` at the highest reasoning setting) writes a model as a pure dataflow intermediate representation the project calls HIR (`@func` SSA-as-DAG), uses the `tilefoundry` command-line tool to `check`, `analyze` (compute cost, roofline, performance per dimension binding), `schedule` and `finalize` it into TIR, and then writes the TileLang (or CuTeDSL, CUDA C, Apple AMX) kernels that implement the scheduled program. The README states the design position in one line: *"Not an agent that becomes the compiler, and not an agent plugged in as one of its passes. The compiler stays a tool — the agent is simply the one holding it."* The compiler supplies analysis and checking; the agent makes the scheduling, segmentation and fusion decisions and writes the kernels.

The repository's evidence is a set of worked examples, each "a real agent run kept whole": the prompt, the agent's budget (hours and tool calls), the artifacts, a correctness report, and a benchmark table against SGLang measured on the same card. Three are load-bearing for this survey.

## Summary

**Qwen3.8-27B prefill (October 2026; `examples/qwen3_8_27b_prefill-tilelang`, verified against `main` at `f8fd71ea` on 13 October).** A 64-layer gated-delta-net / attention hybrid, batch 1, no history, bf16, prompt lengths 1024 / 4096 / 8192; token ids in, first token out. One agent run: 14.88 h, 1,434 tool calls, no sub-agents, five context compactions, two human turns (the prompt and one sentence about which GPU to use). The SGLang 0.5.21 baseline was measured beforehand on the same H200 and handed to the agent as a table with two columns (forward-only and end-to-end), each with its stated flaw and an unexplained 9.1% disagreement at 8192; the agent was told not to re-measure SGLang and had to argue which column is comparable (it chose end-to-end, the column that is stricter at the two long lengths, and reports that it is ahead under either column).

| Prompt | TileFoundry (median of 7, range) | SGLang 0.5.21 | Difference | Compute floor | TFLOP/s (% of 989) |
|---:|---:|---:|---:|---:|---:|
| 1024 | 80.29 ms (80.02–82.61) | 89.06 ms | −9.8% | 51.5 ms | 634.6 (64%) |
| 4096 | 309.61 ms (306.90–315.89) | 317.11 ms | −2.4% | 208.6 ms | 666.2 (67%) |
| 8192 | 631.19 ms (629.11–670.55) | 638.25 ms | −1.1% | 423.8 ms | 664.1 (67%) |

Protocol on the TileFoundry side: one forward pass from token ids on the device to the first token on the device, no scheduler, sampling server, detokenizer or inter-process communication; two untimed warm-ups then seven timed runs, median with range, a different prompt per repeat, SM clock read after every replay (the card sits at 1500 MHz under load; the 8192 row drifts to 1365–1500 MHz). The table was re-measured in a fresh virtual environment on 13 October and agreed within 0.5%. **The SGLang side is a different instrument.** The README describes the timing as forward-only "on either side", but the SGLang figures in the table are column B of `SGLANG_BASELINE.md`: end to end through `meta_info.e2e_latency`, median of seven, premeasured on 12 October and not re-run alongside TileFoundry, with run-to-run ranges of 11.80 / 37.43 / 32.09 ms at 1024 / 4096 / 8192. The file adds that, under the same protocol, a request that does almost nothing (4 tokens) takes 42.65 ms, which it attributes to the scheduler loop's fixed cost of waking from idle. That cost has not been subtracted from column B, and the file warns that subtracting it would put the 1024-token figure below its own 51.5 ms compute floor (FLOP divided by 989 TFLOP/s, H200 bf16 dense), "which is direct evidence that subtracting it is wrong". Column B therefore cannot be converted to a forward-only figure by removing a constant. The same file's column A (forward only, median of three) gives 86.94 / 319.94 / 696.38 ms with ranges of 0.56 / 2.25 / 0.71 ms and disagrees with column B by 9.1% at 8192 for a reason the file does not explain. Against column B, none of the three differences (8.8 / 7.5 / 7.1 ms) exceeds the baseline's own range; against column A the TileFoundry rows are faster at all three lengths, but column A was not the agent's chosen comparator and is a three-run median. Neither column is a paired measurement. Correctness: 18 of 18 per-function checks of the authored HIR against the published model's activations at each length; 54 of 54 checks of the kernels against the HIR; first token identical to `transformers` at all three lengths with maximum absolute logit error 0.25 / 0.38 / 0.85. Every tolerance is derived from where the implementation rounds (one bf16 landing is one step, `rtol = 2^-7`), except `delta_rule`, whose bound was widened after a failure and is reported with its measured margin (0.031 against 0.073). The segmentation decision is argued with a seven-length sweep over four forced GEMM decompositions: at 1024 tokens the wrong choice costs 18%; by 4096 all four are within 0.6%.

**Qwen3.8-27B prefill at 128–1024 tokens (15 October; `…_prefill_short-tilelang`).** Same model, lengths 128 / 256 / 512 / 1024, interleaved measurement against SGLang 0.5.21 (both workers in one process on one card, alternating round by round; three warm-ups and six rounds of ten timed iterations per side, median of sixty; a stubbed forward as negative control) — a different protocol from the premeasured baseline above, and the two must not be pooled: 19.57 / 26.37 / 44.02 / 82.66 ms against 36.84 / 37.16 / 48.54 / 85.41 ms, that is **1.88× / 1.41× / 1.10× / 1.03×**; first token identical to `transformers` and to SGLang at all four lengths. These ratios describe the state at which the task's acceptance criteria were met: the README says the code in the directory is "one optimization pass newer" and that the end-to-end re-measure of the newer state is "not in this directory", so they are not a benchmark of the latest kernel snapshot. Budget: 12.28 h, 1,735 tool calls (586 on the main line, 1,149 in five sub-agents). The run concluded that the four lengths need four implementation sets because the workload crosses the roofline ridge between 128 and 256 tokens; serving 128 tokens from the 256-token implementation costs +35.6% on the forward.

**Nemotron-3.5-Lightning-30B-A3B decode (31 August; `nemotron_3_5_lightning_30b_a3b-tilelang`).** A 52-layer Mamba2 / attention / mixture-of-experts hybrid implemented as one cooperative kernel per decode step (one launch against 3,212 on the op-by-op path), 64 of 64 greedy tokens identical to `transformers`. **It does not beat SGLang**: 287.4 tok/s against 294.8 at context 32 (97.5%) and 231.6 against 278.2 at 262,080 (83.2%), 2.37–2.44× off the measured bandwidth floor at all nine lengths, SGLang measured on the same card the same day with its defaults and no speculative decoding on either side. Budget: 12.24 h, 1,124 tool calls. The report attributes about half of the remaining gap to issue density rather than bandwidth, from a clock sweep.

**Qwen3-1.7B decode (4 August; the README's quick start).** 612.5 tok/s on one H200 (batch 1, bf16, greedy, 2,048 new tokens) from a thirteen-line prompt, 2.1 h and 177 tool calls; 255 of 256 teacher-forced positions agree with Hugging Face. No SGLang comparison is reported for this example; the only ratio is 41× over the same HIR run through TileFoundry's own evaluator (14.8 tok/s), which is not a serving baseline.

Other examples (Qwen3.5-35B-A3B, MiniCPM3-4B in CuTeDSL, granite-4.0-h-small in CUDA C, Qwen prefill on Apple AMX, an FSDP/HSDP training step in HIR) were not read in detail.

## Key takeaways

- **Denominator.** The headline numbers are whole-model prefill latency and decode throughput on one H200, not kernel time. That is the application denominator the 2027 predicate asks for.
- **Baseline.** SGLang 0.5.21 with its default configuration is a strong, widely deployed non-agent serving system, but it is a *system* baseline, not a matched-budget non-agent optimizer over the same actions (there is no "TileFoundry with default schedules" or "human expert with TileFoundry" arm). The 128-token result (1.88×) is largely SGLang's fixed per-forward overhead at short prompts. Two protocols must be kept apart: in the **interleaved** short-prefill run the 128- and 256-token gains are clear application measurements within the example; in the **premeasured** 1024–8192-token run the margins (8.8 / 7.5 / 7.1 ms) are smaller than the SGLang end-to-end column's own run-to-run ranges (11.80 / 37.43 / 32.09 ms), so they are not shown to exceed measurement uncertainty. (Corrected 16 November after ChatGPT's review; the first version of this digest said the 1024-token row cleared it.)
- **Correctness contract.** Derived rather than tuned tolerances, per-function checks against the published model's activations, and first-token identity are a stronger acceptance protocol than the tolerance-only checks most kernel benchmarks use; the reports also state what the end-to-end logit error does *not* measure (rounding growth through 64 layers, which moves 0.85 → 1.50 when only a block size changes).
- **Budget.** 12–15 hours and 1,100–1,700 tool calls per model for the large examples, 2.1 hours for the small one; no token or dollar figure is given, and each example is one run, so there is no variance or success-rate estimate across attempts.
- **Failures.** The per-change logs and rejected candidates stay in a "round archive" that is not in the repository; the published reports list only the derivation failures of the tolerance bounds (eight functions whose first failure was the derivation's fault, not the kernels'). The Nemotron example is an honest shortfall against the baseline and is reported as such.
- **Supplied knowledge.** The prefill runs were given a page of TileLang "scars" from an earlier loop on the same card, marked as hypotheses; this is the supplied-knowledge pattern seen in AKLR and D2K-Bench, undisclosed in quantity.

## Why it matters for this survey

TileFoundry is the clearest public instance so far of the **2027 predicate's shape**: an agent uses a compiler stack (TileLang through a new scheduling layer) to produce a whole-model implementation, and the result is evaluated at the application level against a strong conventional system, with the acceptance protocol, budget and measurement conditions written down. It enters the §5.5.1 running tally as a **candidate, not qualifying** (agreed by both agents, 16 November). The decisive clause is integration: the predicate counts "a compiler/serving integration … adding an optimization action or target backend", and these are standalone worked examples in which the agent uses TileFoundry's own tool, not an action or backend added to a separately shipped compiler or serving path. The failure record is the second gap: hours, tool calls and some rejected attempts are reported, but not the complete set of failed candidates. The lack of a budget-matched non-agent arm is recorded as a causal caveat, not as a further hard requirement of the predicate. A dated first-party demonstration of an agent-derived action or backend in a shipped path (the README's statement that optimizations were shipped to TileOPs is the lead to check), with the full acceptance and failure record, would reopen the count; tile-ai would still be one organization of the two the predicate requires.

It also bears directly on two §6 questions. On **how much of the compiler agents should replace**, it is a third position beside "agent as pass" and "agent as compiler": the compiler stays a deterministic tool with analysis and checking, and the agent owns every decision that the schedule search would otherwise own. On **one kernel language or several**, it demonstrates one HIR with TileLang, CuTeDSL, CUDA C and Apple AMX backends, but reports comparative numbers only for TileLang on H200. The Nemotron result is a useful counterweight for the megakernel trend: a single-launch decode step that is correct and 17% behind the op-by-op serving system at long context, with the gap diagnosed rather than hidden.

Lineage: same organization as [TileLang](tilelang.md) (Peking University · Microsoft Research · Imperial College London in the paper; the tile-ai organization on GitHub) and the TileOPs library, to which TileFoundry optimizations are reported as shipped; the quick-start example overlaps the task class of [KernelBench](kernelbench.md)-style decode kernels but is whole-model. Read beside [MPK](mpk.md) and [Ada-MK](ada-mk.md) (non-agent megakernel compilers), [Magnitude](magnitude.md) (a non-agent on-device tuner with full-engine numbers) and [KernelEvolve](kernelevolve-blog.md) (production agent results with private workloads). The 4 November discovery entry in `AGENTS.md` names TileFoundry as a source earlier sweeps missed; it reached the ledger on 8 November and was digested here once the repository could be read.

**Experiment that would settle the predicate question:** rerun the Qwen3.8-27B prefill task with (a) a second, independent agent and model, (b) a non-agent arm — TileFoundry's own default schedules or a human TileLang expert at the same wall-clock budget — and (c) SGLang re-tuned for batch-1 prefill, reporting three seeds, tokens and dollars, and the rejected-candidate log; then a second organization doing the same on a different model family.

## Limits / caveats

- One organization, one GPU model (H200), batch 1 and no history on every reported row; nothing on multi-GPU, larger batches, or a second vendor beyond the unmeasured Apple AMX example.
- The baseline is SGLang's default configuration measured once per example, not a tuned serving configuration; at 128 tokens its fixed costs dominate, which inflates the short-prompt ratios.
- One agent run per example, no repeats, no token or dollar accounting, and the rejected-candidate record is not published; the reports are written by the agent that produced the result and were "verified" by re-measurement, not by an independent party.
- The agent was given a pre-measured baseline and, in the prefill runs, a page of TileLang notes; the quantity and effect of supplied knowledge are not measured.
- The blog posts stating the platform's position were not readable on this runner; the position is quoted from the README.
- Nothing in the repository's continuous integration re-runs the examples ("Nothing in CI re-runs it"), so the numbers are tied to the stated TileLang and `tilefoundry` versions.
